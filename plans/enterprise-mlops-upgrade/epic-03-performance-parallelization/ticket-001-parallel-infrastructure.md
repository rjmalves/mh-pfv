# E03-T001 Add future/future.apply Dependency and Parallel Infrastructure

## Context

### Background

The mhpfv package processes solar PV plants sequentially via `lapply` in both `train_main()` and `predict_main()`. With production workloads spanning dozens to hundreds of plants, this is the primary bottleneck. The `future` and `future.apply` packages provide a drop-in replacement for `lapply` that enables transparent parallelism with minimal code changes. This ticket establishes the parallel infrastructure that E03-T002 and E03-T003 will use.

### Relation to Epic

This is the foundation ticket for Epic 03 (Performance and Parallelization). It adds the `future`/`future.apply` dependencies, creates a configuration helper module (`R/parallel.r`), and ensures the package can set up and tear down parallel backends. No pipeline code is changed yet -- that happens in E03-T002 and E03-T003.

### Current State

- `DESCRIPTION` imports: `data.table`, `argparse`, `lgr`, `lubridate`, `pfvIO`, `arrow`. No parallelism packages.
- `R/mh-pfv.r` has `@import utils stats` and `@import data.table argparse lgr pfvIO`. No future imports.
- `NAMESPACE` is generated by roxygen2 and lists imports for the packages above.
- There is no `R/parallel.r` file.
- `cli_main()` in `R/cli.r` dispatches to `train_main()` or `predict_main()` without any parallel plan setup.

## Specification

### Requirements

1. Add `future (>= 1.34.0)` and `future.apply (>= 1.11.0)` to `Imports` in `DESCRIPTION`.
2. Create `R/parallel.r` with:
   - `setup_parallel_plan(workers = NULL, strategy = "multisession")` -- configures `future::plan()`. If `workers` is `NULL`, defaults to `future::availableCores() - 1L` (minimum 1). Returns the previous plan invisibly for later restoration.
   - `reset_parallel_plan(old_plan)` -- restores a previous plan (wraps `future::plan(old_plan)`).
   - `get_parallel_config()` -- returns a list with `workers` count and `strategy` name for logging/diagnostics.
3. Use `future::plan(strategy, workers = workers)` internally. Default to `multisession` (not `multicore`) because `multicore` is unsafe on Windows and inside RStudio. The `strategy` parameter allows overriding for environments where `multicore` is preferred (e.g., Linux-only Docker containers).
4. Do NOT modify `cli_main()`, `train_main()`, or `predict_main()` in this ticket. Infrastructure only.
5. All three functions must be exported and documented with roxygen2.
6. Add `@importFrom future plan availableCores` and `@importFrom future.apply future_lapply` in `R/parallel.r` so they are registered in NAMESPACE.

### Inputs/Props

- `setup_parallel_plan(workers, strategy)`:
  - `workers`: integer or `NULL`. When `NULL`, auto-detect with `availableCores() - 1L`.
  - `strategy`: character, one of `"multisession"`, `"multicore"`, `"sequential"`. Default `"multisession"`.
- `reset_parallel_plan(old_plan)`:
  - `old_plan`: the object returned by a prior `setup_parallel_plan()` call.
- `get_parallel_config()`: no arguments.

### Outputs/Behavior

- `setup_parallel_plan()` returns the previous `future::plan()` invisibly (so callers can restore it). Logs the plan configuration via `lgr`.
- `reset_parallel_plan()` restores the previous plan. Returns `invisible(NULL)`.
- `get_parallel_config()` returns `list(workers = <int>, strategy = <string>)`.
- When `strategy = "sequential"`, the future plan is set to sequential (backward-compatible, no parallelism). This is the escape hatch for environments where parallelism causes issues.

### Error Handling

- If `workers` is not `NULL` and not a positive integer, stop with a clear error message.
- If `strategy` is not one of the allowed values, stop with a clear error message.
- If `future` or `future.apply` are not installed (e.g., in a degraded environment), the functions should fail with an informative error from the normal R import mechanism (no special handling needed since they are in `Imports`).

### Patterns to Follow

- Roxygen2 documentation style from `R/model-strategy.r`: Portuguese descriptions, `@param`, `@return`, `@details`, `@seealso`, `@export`.
- Function naming: snake_case, descriptive verbs (e.g., `setup_parallel_plan`, not `par_setup`).
- Tests follow the nested `test_that()` pattern from `tests/testthat/test-utils.r`.
- Use `withr::defer()` or `on.exit()` patterns for cleanup in tests to restore sequential plan after each test.

### Pitfalls to Avoid

- Do NOT use `@import future` or `@import future.apply` -- use `@importFrom` to avoid importing all symbols from these large packages.
- Do NOT set a parallel plan at package load time (in `.onLoad` or `R/zzz.r`). Plans must be explicitly set by the caller.
- When testing, always restore the plan to `sequential` after each test to avoid leaking parallel state between tests. Use `withr::defer(future::plan("sequential"))` at the start of each test that sets up a plan.
- `availableCores()` can return 1 on CI environments. Ensure `max(1L, availableCores() - 1L)` so workers is never zero.
